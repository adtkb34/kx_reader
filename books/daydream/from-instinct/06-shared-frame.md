{#claim}
## 主张

多人了解同一事务时，优先**约定一套共用框架**：先声明怎么切开，再让各角色在同一坐标上看自己相关的切片。框架是契约，不是事务自带的唯一真相——换用途、换人群，允许换轴。

{#object-frame-slice}
## 对象、框架、切片

| 词 | 指什么 |
| --- | --- |
| 对象 | 大家大致在谈同一件事 |
| 框架 | 约定的主切法 / 坐标 |
| 切片 | 某人真正深挖的那一枝或那几维 |

有共同对象 ≠ 已有共同框架。有共同框架 ≠ 每人走完所有枝。

{#limits}
## 限度

1. 主轴对某角色处处别扭、只能靠心智换算 → 换轴，或加第二视图（标签、矩阵、另树）。  
2. 强行「万事只有这一套」会把未选轴伪装成已共用，滑向 [维度错位](07-dimension-mixup.md#claim)。  
3. 一份主目录 + 若干旁路找法，往往比幻想一棵树伺候所有人更诚实。

同级混尺 → [维度错位](07-dimension-mixup.md#claim)；轴已定却粗细乱 → [层级错位](08-hierarchy-mixup.md#claim)。

{#examples}
## 例子

:::details 软件协作
团队约定「先按模块挂，再挂具体项」。测试也可先选模块再落到用例——与开发同图，切片不同。按关键路径 / 风险先切往往也成立。
:::

:::details 需求与实现
产品按用户任务讲，研发按服务边界讲。从不声明两套坐标如何对照，评审会各执一图。
:::

:::details 组织对齐
业务线与专业线都能描述同一个人的工作。共用哪张汇报图是契约；另一维用虚线、矩阵或双线汇报补。
:::
