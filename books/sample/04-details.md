{#basics}
## 基本用法

一个小节的正文给结论，细节进折叠块。比如：**该服务的限流策略是令牌桶，默认每秒 100 个请求。**

:::details 限流的完整配置与默认值
| 配置项 | 默认值 | 说明 |
| --- | --- | --- |
| `rate` | 100/s | 令牌生成速率 |
| `burst` | 200 | 桶容量，允许的瞬时突发 |
| `key` | 客户端 IP | 限流维度 |
| `on_reject` | 429 | 超限时返回的状态码 |

```yaml
rate_limit:
  rate: 100
  burst: 200
  key: client_ip
  on_reject: 429
```
:::

:::details 为什么选令牌桶而不是滑动窗口
滑动窗口在窗口边界处有两倍突发的问题；令牌桶的突发上限由桶容量显式控制，语义更直观，实现也只需要两个计数器。
:::

{#nested}
## 嵌套折叠

折叠块可以嵌套：外层用四个冒号，内层用三个。适合「细节里还有更细的细节」的场景。

::::details 部署拓扑（展开后内部还有一层）
服务部署在两个可用区，各一组无状态实例，共享一个主从数据库。

:::details 每个可用区的具体实例规格
##### 实例规格明细 {#az-spec}

- 应用实例：2 vCPU / 4 GB × 3
- 数据库：4 vCPU / 16 GB，主从半同步复制
- 缓存：单节点 2 GB，允许击穿回源
:::
::::

折叠块内部的 `{#id}` 独占行不切节。需要块内跳转锚点时，可在标题行尾写 `{#id}`（只生成 HTML id，不是小节边界）——比如从别处链接到 [实例规格明细](#az-spec)，阅读器会自动展开它所在的折叠块再定位。

## 原始数据样例

结论：**近 30 天 P99 延迟稳定在 180ms 以内，无需扩容。**

:::details 支撑该结论的原始数据
```json
{
  "window": "30d",
  "p50_ms": 42,
  "p95_ms": 121,
  "p99_ms": 178,
  "max_qps": 8600,
  "error_rate": 0.0004
}
```

采样说明：数据来自网关侧全量访问日志，剔除了健康检查流量；P99 按天聚合后取 30 天最大值，属于保守口径。
:::
